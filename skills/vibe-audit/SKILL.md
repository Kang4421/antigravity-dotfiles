# Vibe Audit (Full-Spectrum Autonomous QA & Design Auditor)

사용자가 일일이 "이거 테스트해라, 저거 확인해라" 지시하지 않아도, 에이전트가 코드를 스스로 분석하여 **개발 의도를 역추적하고, 테스트 시나리오를 자율 도출하며, 도메인에 맞는 최적의 검증 드라이버(ego-browser, 임시 하네스, CLI 파이프, API 클라이언트)를 투입해 A부터 Z까지 전방위로 실측 감사하는 엔진**이다.

웹 UI의 레이아웃·반응형 디자인부터 CLI의 터미널 사용자 경험(DX), 백엔드의 엣지 페이로드 복원력, 라이브러리의 인터페이스 안정성까지 모든 소프트웨어 도메인을 아우른다.

---

## 5대 핵심 감사 철학 (Core Principles)

1. **전권 위임 자율성 (Delegated Autonomy)**:
   사용자에게 테스트 케이스를 묻지 않는다. 코드, README, git diff, 함수 시그니처로부터 "이 프로그램이 달성해야 할 궁극적 목적과 사용자 가치"를 스스로 역추적하여 테스트 매트릭스를 직접 수립한다.
2. **도메인 불가지론 (Domain-Agnostic Drivers)**:
   웹 브라우저에 매몰되지 않는다. 프로젝트의 본질이 Web인지, Backend API인지, CLI인지, Module/SDK인지, Data Script인지 자동 감별하여 해당 도메인에 최적화된 감사 드라이버를 스스로 선택·가동한다.
3. **삼위일체 전방위 검증 (Tri-Axis Audit Matrix)**:
   모든 감사는 반드시 아래 3개 축을 모두 포괄해야 한다:
   - **축 1. 기능 완결성 (Functional & Logic)**: 정상적인 흐름(Happy Path)이 의도대로 정확하게 완주되는가?
   - **축 2. 인간 공학 및 경험 (Visual & Ergonomics / UX / DX)**: 웹은 비주얼 마감·반응형·색상 대비를 실측하고, CLI/API는 도움말 가독성·에러 메시지 친절도·종료 코드 일관성을 실측한다.
   - **축 3. 경계값 및 방어력 (Edge & Adversarial)**: 빈 값, null, 극단적 수치, 특수문자, 포맷 오류 주입 시 뻗지 않고 우아하게 방어하는가?
4. **실제 조작 기반 증거주의 (No Speculation, Action-First)**:
   코드를 눈으로만 읽고 추측 평가하지 않는다. 웹은 `ego-browser`로 직접 버튼을 누르고 화면을 캡처하며, CLI/API/모듈은 명령어를 실제로 쏘거나 임시 하네스를 띄워 실제 반환값과 상태 코드를 확인한다.
5. **무손실 안전 수칙 (Safe Teardown & Preservation)**:
   감사를 위해 기동한 테스트 서버, 브라우저 탭, 백그라운드 프로세스는 감사 종료 즉시 완전히 정리(Kill)한다. 또한 수정 작업(`--fix` 모드) 시 사용자의 기존 작업물을 파괴하거나 임의 롤백하지 않는다.

## 도메인별 5대 감사 드라이버 (Domain Drivers)

프로젝트 스캔 후 감지된 도메인에 따라 해당 드라이버(복수 개일 경우 병렬)를 가동한다:

```text
[프로젝트 식별] ──► Web UI: [Driver 1] ego-browser 실조작 및 비주얼/반응형 감사
                ──► Backend API: [Driver 2] 가상 클라이언트 REST/GraphQL 페이로드 실측
                ──► CLI / 도구: [Driver 3] 옵션 조합 및 에러 메시지 DX 감사
                ──► 라이브러리/SDK: [Driver 4] 임시 스크립트 자율 생성 및 API 계약 검증
                ──► 데이터/스크립트: [Driver 5] Mock 데이터 주입 및 멱등성/파이프라인 검증
```

### [Driver 1] Web Application & Frontend UI
- **도구**: `ego-browser` (또는 내장 `browser` 서브에이전트)
- **비주얼 & 디자인 감사 (Visual & UX)**:
  - 뷰포트 반응형 실측: 모바일(375×812), 태블릿(768×1024), 데스크톱(1440×900)으로 창을 리사이즈하며 렌더링 확인.
  - 레이아웃 깨짐, 텍스트 넘침(Overflow), 컴포넌트 겹침, 여백(Padding/Margin) 불균형, 폰트/색상 대비 실측.
- **인터랙션 및 엣지 조작**:
  - 정상 조작: 폼 입력, 드롭다운 선택, 버튼 클릭, 페이지 라우팅, 모달 팝업 열기/닫기.
  - 악의적 조작: 빈 폼 제출, 글자수 한계 초과 입력, 자바스크립트 인젝션 스크립트(`<script>alert(1)</script>`) 입력 시 XSS 방어 및 에러 토스트 표시 실측.
- **실시간 감시**: 브라우저 콘솔 에러(0건 원칙) 및 Network 탭 4xx/5xx 실패 요청 전수 추적.

### [Driver 2] Backend API & Server Services
- **도구**: 쉘 런타임(`curl`, `Invoke-RestMethod`, HTTP 클라이언트)
- **엔드포인트 전수 호출**:
  - 정상 호출: 명세된 파라미터 전달 시 올바른 HTTP 상태 코드(`200`, `201`) 및 JSON 스키마 반환 여부.
  - 엣지 호출: 필수 필드 누락, 잘못된 데이터 타입(문자열 필드에 숫자, 음수 ID 등) 주입 시 `400 Bad Request`와 명확한 원인 메시지를 반환하는지 실측(서버 500 크래시 원천 차단).
  - 인증/인가: 무인증 접근 시 적절한 `401 Unauthorized` / `403 Forbidden` 차단 확인.

### [Driver 3] CLI & Command-Line Tools
- **도구**: Windows PowerShell / CMD 터미널
- **인간공학(DX) 감사**:
  - `--help`, `-h` 실행 시 옵션 설명이 일목요연하고 예시(Usage)가 포함되어 있는가?
  - `--version`이 명시된 버전과 일치하는가?
- **입출력 및 에러 처리 실측**:
  - 필수 인자 누락 시 "사용법"을 친절하게 안내하고 `Exit Code != 0`으로 종료하는가?
  - 알 수 없는 잘못된 플래그 입력 시 프로그램이 Unhandled Exception(파이썬 트레이스백 날것 노출 등)으로 죽지 않고 정제된 에러를 출력하는가?
  - 정상 실행 시 파이프라인 친화성(JSON 출력 옵션 등) 지원 여부 확인.

### [Driver 4] Module, Library & SDK
- **도구**: 인메모리 임시 하네스 스크립트 (Node.js/Python/Go/Rust 등)
- **인터페이스 검증**:
  - 공개된(Public) 핵심 함수, 클래스, 메서드를 직접 import하는 임시 스크립트를 작성하여 실행.
  - 반환값의 타입 안정성, Promise/Async 예외 처리, Nullable 파라미터 처리 확인.
  - 검증 완료 후 임시 하네스 스크립트는 안전하게 삭제/정리.

### [Driver 5] Data Pipeline & Batch Scripts
- **도구**: Mock 데이터 셋 및 테스트 파일
- **파이프라인 무결성**:
  - 결측치(NaN, Null), 비정상 포맷의 행(Row), 초대용량 더미 데이터를 투입했을 때 크래시 없이 격리(DLQ)하거나 스킵하는지 확인.
  - 멱등성(Idempotency): 동일한 입력을 2회 연속 실행했을 때 중복 저장이나 에러 없이 일관된 결과를 유지하는지 실측.

## 5단계 자율 감사 워크플로 (5-Phase Workflow)

### Phase 1: 아티팩트 및 의도 역추적 (Reconstructed Intent)
1. 코드베이스 구조, 최근 변경 내역(`git diff`), 문서(README, 주석, 인터페이스 정의)를 읽는다.
2. 이 프로그램의 **핵심 존재 목적(Core Mission)**과 **주요 사용자 페르소나**를 스스로 규정한다.

### Phase 2: 삼위일체 테스트 매트릭스 자율 수립 (Matrix Synthesis)
1. 질문 없이 에이전트 스스로 3가지 축(기능 / 디자인·UX / 엣지·보안)의 최소 5~10가지 구체적 테스트 케이스를 수립한다.
2. 예시:
   - Case 1 (Happy): 정상 데이터 입력 후 최종 결과 생성 검증
   - Case 2 (Visual/UX): 모바일 뷰포트에서 상단 헤더 및 버튼 겹침 실측
   - Case 3 (Adversarial): 특수문자 및 빈 페이로드 전송 시 유효성 검사 실측
   - Case 4 (Robustness): 외부 API 장애를 가정한 타임아웃 방어 실측

### Phase 3: 도메인 드라이버 실측 및 증거 수집 (Execution & Evidence)
1. 필요 시 백그라운드로 로컬 서버/앱 기동 (종료 추적을 위해 TaskId 기록).
2. 도메인에 맞는 드라이버를 투입하여 수립된 매트릭스를 하나씩 실제로 실행하고 결과를 수집한다:
   - 웹 화면은 스크린샷 파일 생성 및 렌더링 검사
   - 터미널/API는 원시 출력 로그 및 상태 코드 수집
3. 실측이 끝나면 기동했던 모든 백그라운드 프로세스를 즉시 종료(Teardown)한다.

### Phase 4: 자율 디버깅 및 Auto-Fix (`--fix` 활성 시 또는 명백한 결함 시)
1. 감사 도중 발견된 치명적 결함(서버 500 에러, 크래시, 레이아웃 완전 깨짐, 보안 취약점)에 대해 원인을 분석한다.
2. 스스로 코드를 수정하고, 해당 테스트 케이스를 다시 실측하여 해결 여부를 확증한다 (최대 3회 반복).
3. 단순 개선 제안(디자인 취향, 추가 기능)은 임의로 수정하지 않고 리포트의 권고안으로 넘긴다.

### Phase 5: 종합 감사 리포트 (Full-Spectrum Audit Report) 출력
감사 완료 후 단정하고 명확한 구조로 최종 종합 감사 리포트를 사용자에게 제출한다.
