# Vibe Verify (Dynamic Full-Pipeline Verification & Auto-Fix Engine)

바이브코딩이나 기능 구현이 끝난 직후, 코드만 읽고 "정상 구현되었습니다"라고 추측성 완료 선언을 하는 것을 원천 차단하고, **실제 빌드 → 조건부 테스트 → 런타임 프로세스 기동 → 실화면 브라우징 및 콘솔 에러 실측 → 자율 수정(Auto-fix) → 정량적 증거(Proof) 테이블 보고**를 현재 세션에서 완결하는 동적 검증 엔진이다.

---

## 6대 불변의 행동 강령 (Core Constitution)

1. **실측 증거 없는 완료 선언 금지 (No Claims Without Fresh Proof)**:
   코드를 눈으로만 읽고(Static Reading) 정상 동작한다고 판단하는 행위를 엄격히 금지한다. 모든 통과 판정은 반드시 방금 실행한 터미널 명령어의 `Exit Code`와 실제 출력 로그, 브라우저 콘솔 실측 결과에 기반해야 한다.
2. **현재 세션 직접 수행 (Single-Session Direct Execution)**:
   별도의 검증용 서브에이전트로 컨텍스트를 분리하지 않고, 작업 맥락을 완전히 파악하고 있는 현재 메인 세션에서 에이전트가 직접 검증 파이프라인과 자동 수정을 신속하게 수행한다. (단, 웹 UI 실화면 확인 시에만 브라우저 제어 도구를 호출한다.)
3. **무테스트 프로젝트의 테스트 강제 생성 금지 (Zero Test-Bloat Policy)**:
   기존에 테스트 코드나 테스트 스위트가 없는 바이브코딩 프로젝트에서 검증을 명목으로 새로운 단위/통합 테스트 파일이나 임시 검증 스크립트를 임의로 생성하지 않는다. 테스트가 없으면 즉시 빌드 및 실제 런타임/화면 기동 검증으로 직행한다.
4. **치명적 에러 차단 및 경고 관용 원칙 (Fatal-Only Blocking & Warning Tolerance)**:
   - **차단 및 수정 대상 (Blocker)**: 빌드/컴파일 실패, 모듈 누락, 런타임 크래시(Exit Code != 0), Unhandled Exception, HTTP 5xx 응답, 브라우저 개발자 도구 `Console Error` 및 화면 렌더링 백화(Blank Page) 현상.
   - **관용 대상 (Advisory)**: 실행과 동작에 지장을 주지 않는 Linter 스타일 지적, 미사용 변수 경고(Warning), Deprecation Notice 등은 실패로 간주하지 않고 통과시키되, 최종 리포트 하단에 참고 사항으로만 부기한다.
5. **자율 디버깅 3회 하드 캡 및 상태 보존 (3-Strike Auto-Fix & No-Rollback)**:
   검증 단계에서 차단 대상(Blocker) 에러가 감지되면 사용자에게 즉시 되묻지 않고 스스로 원인을 분석해 코드를 수정한 뒤 해당 단계부터 재검증한다. 단, 수정 후 재검증은 **최대 3회(Attempt 1~3)**까지만 허용한다. 3회 시도 후에도 해결되지 않으면 임의로 `git reset`이나 롤백을 수행하지 않고, 현재 수정 상태를 그대로 보존한 채 실패 원인과 에러 로그 전문을 보고하고 대기한다.
6. **프로세스 및 리소스 무결성 정리 (Clean Teardown)**:
   런타임 검증을 위해 백그라운드에서 기동한 로컬 개발 서버, API 서버, 데몬 프로세스는 검증이 끝나는 즉시 `manage_task(kill)` 등을 통해 누락 없이 종료하여 사용자의 포트나 시스템 리소스를 점유하지 않게 한다.

## 4단계 동적 풀 검증 파이프라인 (4-Stage Verification Pipeline)

사용자가 스킬을 호출하면 에이전트는 아래 4단계를 순차적으로 실행한다.

### Stage 1: 프로젝트 환경 및 진입점 자동 식별 (Discovery)
1. 프로젝트 루트의 매니페스트 및 설정 파일을 스캔하여 기술 스택과 실행 명령어를 식별한다:
   - Node.js / TS / 프론트엔드: `package.json` (`scripts` 내 `build`, `typecheck`, `test`, `dev`, `start`)
   - Python: `pyproject.toml`, `requirements.txt`, 메인 엔트리 파일 (`main.py`, `app.py`, `manage.py`)
   - Rust / Go / Java / 기타: `Cargo.toml`, `go.mod`, `build.gradle`, `Makefile` 등
2. 최근 변경된 파일(`git status`, `git diff --stat`)을 확인하여 이번 작업에서 수정·추가된 핵심 모듈과 실행 경로를 파악한다.

### Stage 2: 정적 컴파일 및 빌드 무결성 검증 (Build & Compile Integrity)
1. 프로젝트에 빌드 또는 타입 검사 명령어가 존재하는 경우(`npm run build`, `npx tsc --noEmit`, `cargo check`, `go build`, `python -m py_compile` 등) 이를 실행한다.
2. **판정 기준**:
   - `Exit Code == 0`: 통과 (Warning 출력이 있더라도 에러가 없으면 통과 처리 후 경고 내용만 기록).
   - `Exit Code != 0`: 즉시 **Auto-Fix Loop**를 가동하여 컴파일/번들 에러를 수정하고 재실행한다.

### Stage 3: 조건부 테스트 스위트 실행 (Conditional Test Suite)
1. 프로젝트 내에 **실제 작성된 테스트 파일**(`*.test.*`, `*.spec.*`, `tests/` 등)과 테스트 러너가 이미 존재하는지 확인한다.
2. **분기 처리**:
   - **기존 테스트가 존재하는 경우**: 테스트 러너를 실행하여 회귀 버그 여부를 검증한다. 실패 시 **Auto-Fix Loop**로 진입한다.
   - **기존 테스트가 없는 경우**: 테스트 코드를 새로 작성하지 않고, 증거 테이블에 `해당 없음 (Skip - 기존 테스트 부재)`으로 기록한 뒤 즉시 Stage 4로 넘어간다.

### Stage 4: 동적 런타임 기동 및 실화면 브라우징 검증 (Runtime & UI Verification)
프로젝트의 성격에 따라 아래 트랙 중 해당되는 검증을 수행한다 (풀스택의 경우 Track A와 Track B 모두 수행).

#### [Track A] CLI / 백엔드 API / 일반 스크립트
1. 애플리케이션 또는 서버를 기동한다 (서버의 경우 `run_command`의 백그라운드 대기 또는 데몬 기능 활용).
2. 기동 직후 프로세스가 죽지 않고 정상 유지되는지 확인하고, 로컬 엔드포인트 호출(`Invoke-WebRequest` / `curl`) 또는 CLI 인자 실행을 통해 정상 응답과 종료 코드(`0`)를 확인한다.

#### [Track B] 웹 애플리케이션 / 프론트엔드 UI
1. 로컬 개발 서버(`npm run dev` 등)를 백그라운드로 기동하고 리스닝 포트(예: `localhost:3000`, `localhost:5173`)를 확인한다.
2. **브라우저 실화면 및 콘솔 검증**:
   - 브라우저 도구(`browser` 서브에이전트 또는 `ego-browser`)를 사용하여 해당 로컬 URL에 실제로 접속한다.
   - 확인할 핵심 항목:
     1) 페이지가 빈 화면(White/Blank Screen)이나 프레임워크 에러 오버레이 없이 정상 렌더링되는가?
     2) 브라우저 개발자 도구(DevTools) 콘솔에 `Console Error` 또는 `Uncaught Exception`이 0건인가?
     3) 이번에 구현한 핵심 컴포넌트/화면에 기본 상호작용(클릭/라우팅 등) 시 런타임 에러가 발생하지 않는가?
3. 에러 발견 시 즉시 **Auto-Fix Loop**를 가동하여 수정 후 재검증한다.

#### [Teardown] 백그라운드 프로세스 정리
- Stage 4 검증이 완료(통과 또는 3회 실패 중단)되면, 검증을 위해 띄웠던 백그라운드 개발 서버나 프로세스를 즉시 종료(`manage_task(Action: "kill")`)하고 종료 여부를 확인한다.

## 자율 디버깅 및 자동 수정 프로토콜 (Auto-Fix Loop Protocol)

Stage 2~4 중 어느 단계에서든 차단 대상(Blocker) 에러가 발생하면 아래 루프를 실행한다:

```text
[에러 감지] ──► [원인 및 스택트레이스 분석] ──► [코드 수정 (Attempt N/3)] ──► [실패한 단계부터 재검증]
```

1. **Attempt 1 ~ 3**:
   - 추측성 수정이 아닌 에러 로그의 정확한 파일 경로, 라인 번호, 스택 트레이스를 근거로 원인을 수정한다.
   - 수정 직후 실패했던 검증 명령어(또는 브라우저 접속)를 다시 실행하여 해결 여부를 실측 확인한다.
2. **3회 초과 시 중단 및 보존 (Circuit Breaker)**:
   - Attempt 3 재검증에서도 에러가 해결되지 않으면 추가 수정을 즉시 멈춘다.
   - 지금까지 수정한 코드는 **절대 임의로 롤백(`git checkout`, `git reset`)하지 않고 현 상태 그대로 보존**한다.
   - 최종 리포트 판정을 `실패 (수동 확인 필요)`로 표기하고, 3회 시도한 내역과 미해결 에러 로그를 투명하게 보고한다.

## 최종 검증 리포트 출력 규격 (Verification Report Format)

검증 파이프라인이 종료되면 군더더기 없이 아래 구조로 최종 리포트를 출력한다.

### 1. 최종 검증 요약
- **최종 판정**: `통과 (PASS)` 또는 `실패 (FAIL - Auto-fix 3회 초과)`
- **검증 대상**: 프로젝트/모듈 경로 및 감지된 기술 스택
- **자율 수정 횟수**: `0회 (초회 통과)` 또는 `N/3회 수행`

### 2. 정량적 실행 증거(Proof) 테이블
실제 실행한 명령어와 결과를 한눈에 볼 수 있는 표로 제시한다 (실행하지 않은 항목을 거짓으로 기재하는 행위 엄격 금지):

| 검증 단계 | 실행 명령어 / 도구 | Exit Code / 상태 | 판정 | 실측 증거 및 핵심 로그 스니펫 |
| :--- | :--- | :---: | :---: | :--- |
| **1. 빌드/컴파일** | `실제 실행한 명령어` | `0` | 통과 | `출력된 성공 메시지 또는 소요 시간 요약` |
| **2. 테스트 스위트** | `실행 명령어` 또는 `-` | `0` 또는 `Skip` | 통과 / 생략 | `N passed` 또는 `기존 테스트 코드 없음 (Skip)` |
| **3. 런타임 기동** | `실행 명령어` | `0` / `Running` | 통과 | `포트 바인딩 로그 및 프로세스 정상 기동 확인` |
| **4. 화면/응답 실측** | `Browser` / `HTTP 호출` | `200 OK` | 통과 | `렌더링 정상 확인, Console Error 0건 (리소스 정리 완료)` |

### 3. 자율 수정(Auto-Fix) 이력 *(※ 수정이 발생한 경우에만 출력)*
- **[Attempt N]**:
  - **감지된 에러**: 단계 및 핵심 에러 메시지 요약
  - **수정 내역**: 수정한 파일 링크 및 조치 내용
  - **재검증 결과**: 해결 완료 여부

### 4. 참고용 경고 사항 (Advisory Warnings) *(※ Warning이 존재할 때만 출력)*
- 동작에는 이상이 없으나 빌드/린트 과정에서 출력된 Warning 내역을 간략히 불릿으로 정리하여 사용자에게 참고 정보로 제공한다.
- *(3회 실패로 중단된 경우 이 섹션 대신 **[미해결 에러 상세 및 재현 경로]** 섹션을 출력하여 사용자가 이어서 판단할 수 있도록 돕는다.)*
