# Execution Plan (Universal Implementation Planning Engine)

확정된 사양서나 요구사항을 전달받았을 때, 곧바로 코딩이나 본 작업에 돌입하지 않고
**사전 실사 → 계획서 생성 → 명시적 승인 게이트 → 실행·검증 → 워크스루(Walkthrough)**의 4단계 라이프사이클을 엄격히 통제하는 전 도메인 범용 실행 플래닝 엔진이다.

---

## 4대 불변의 행동 강령 (Core Constitution)

1. **조기 실행(Premature Execution) 절대 금지 [Execution Lock]**:
   사용자가 계획서(Plan)를 명시적으로 승인("진행해", "좋아", "승인", "Proceed")하기 전까지는 **단 한 줄의 실제 코드 수정, 본 파일 생성, 상태 변경성 쉘 명령 실행을 절대 하지 않는다.** (사전 탐색용 읽기 명령이나 계획서 마크다운 생성만 허용)
2. **팩트 기반 사전 실사 (Fact-First Due Diligence)**:
   추측이나 기억에 의존해 계획을 세우지 않는다. 계획서를 작성하기 전에 반드시 코드베이스, 디렉터리, 기존 문서, 환경 설정, 리소스 현황을 직접 조사(Tool 호출)하여 팩트를 먼저 확립한다.
3. **구체적이고 검증 가능한 단계별 마일스톤 (Actionable & Verifiable)**:
   "모듈 구현", "UI 작업" 같은 추상적 계획을 금지한다. 각 단계(Step)마다 정확히 어떤 파일의 어느 영역을 건드리는지, 산출물이 무엇인지, 무엇으로 완료를 증명(테스트/검증 명령)할지 구체적으로 명시한다.
4. **자체 검증 및 워크스루 의무 (Self-Verification & Walkthrough)**:
   작업이 끝났다고 성급히 종료하지 않는다. 사양서와 계획서에 정의된 '성공 기준' 및 테스트를 직접 통과시켰는지 실측 검증한 뒤, 최종 변경 요약과 증거를 담은 워크스루(Walkthrough) 리포트로 마감한다.

---

## 4단계 실행 프로토콜 (4-Stage Protocol)

### Stage 1: 사전 환경 및 자료 실사 (Due Diligence)

본격적인 계획 수립 전, 현재 작업 환경과 필요한 리소스를 철저히 조사하고 진행 상황을 사용자에게 간략히 공유한다.

- **개발 / 소프트웨어 엔지니어링**:
  - 관련 소스 코드, 디렉터리 구조, 의존성(`package.json`, `requirements.txt` 등) 정밀 확인
  - 기존 함수/클래스 시그니처, 인터페이스, DB 스키마, 설정 파일 조회
  - 현재 빌드/테스트 명령어 및 통과 여부 사전 확인
- **기획 / 비즈니스 / 전략**:
  - 확정된 사양서(`.agents/specs/spec-*.md`), 관련 기획 문서, 기존 정책 데이터 조회
  - 기술적/법적/운영 제약 조건 재확인
- **일상 / 라이프스타일 / 기타**:
  - 세부 일정, 예산, 가용 도구, 선행 조건 및 리소스 제약 실사

---

### Stage 2: 실행 계획서(Plan) 생성

실사 결과를 바탕으로 작업 단위가 명확히 쪼개진 상세 실행 계획서를 작성한다.

* **저장 위치**:
  - 파일 모드 (기본): `.agents/specs/plan-{slug}.md` (단, 직전 `deep-interview`가 `--chat(-c)` / `--no-spec`으로 진행되어 사양서 파일이 없는 경우에는 자동으로 채팅 모드로 전환)
  - 채팅 모드 (`--chat` 또는 `-c`): 파일 생성 없이 채팅창 내 정밀 체크리스트로 출력
  - Antigravity 아티팩트 환경 지원 시: 아티팩트 디렉터리 내 `<plan_name>.md` 생성 가능
  
#### 실행 계획서 표준 템플릿
```markdown
# [Plan] {작업명 또는 태스크 제목}

## 1. 개요 및 참조 기준
- 참조 사양서: `.agents/specs/spec-{slug}.md` (또는 사용자 요구사항)
- 핵심 목표: {1~2줄 요약}
- 전제 조건 및 사전 실사 결과: {실사에서 확인된 핵심 사실}

## 2. 작업 대상 인벤토리 (※ 비개발/기획 작업 시 '산출물 및 리소스 목록'으로 대체)
- 수정 대상: `경로/파일명` (수정 범위: 함수/클래스명 또는 문서 섹션)
- 신규 생성: `경로/파일명` (또는 신규 산출물)
- 삭제/이동 대상: {해당 시 기재, 파일 삭제 시 휴지통 정책 준수}

## 3. 단계별 실행 계획 (Step-by-Step Milestones)
- **Step 1: {단계 명칭}**
  - 세부 작업: {구체적인 변경/생성 내용}
  - 변경 대상: `경로/파일명`
  - 검증 방법: {확인할 명령어, 테스트 케이스, 수동 점검 항목}
- **Step 2: {단계 명칭}**
  ...
- **Step N: {최종 통합 및 검증}**

## 4. 검증 및 테스트 전략
- 검증 방법 / 명령어: (개발 시 `npm test`, `pytest` 등 실행 명령어 / 기획·문서 작업 시 사양서 요구사항 대조 체크리스트)
- 엣지 케이스 및 예외 처리 검증 항목
- 성공 판정 기준 (사양서 기준 충족 여부)

## 5. 리스크 및 비상 대책 (Plan B / Fallback)
- 잠재 장애 요인 및 실패 시 즉시 롤백/우회 시나리오
```

---

### Stage 3: 명시적 승인 게이트 (Approval Gate)

계획서를 출력하거나 생성한 즉시 **모든 도구 호출을 멈추고 사용자의 명시적 승인을 기다린다.**

#### 사용자 질의 출력 형식
> **[📋 실행 계획서 수립 완료]**  
> 계획서 경로: `.agents/specs/plan-{slug}.md`  
> 
> 위 실행 계획대로 본 작업을 진행할까요?  
> 수정하거나 추가·제외할 단계가 있다면 말씀해 주세요. 사용자의 명시적 승인 전에는 실제 파일 변경이나 본 작업을 시작하지 않습니다.

* **사용자 피드백 대응**:
  - 사용자가 수정을 요구하면: 계획서를 즉시 업데이트한 뒤 다시 승인을 구한다.
  - 사용자가 승인("진행해", "좋아", "승인", "OK" 등)하면: 비로소 Stage 4로 진입한다.

---

### Stage 4: 본 작업 실행, 자체 검증 및 워크스루 (Execution & Walkthrough)

승인이 완료되면 단계별 계획에 따라 실제 작업을 차례대로 수행한다.

1. **순차 실행 (Sequential Execution)**:
   - Step 1부터 순서대로 작업을 수행하며, 단계별 진행 상태를 간략히 공유한다.
   - 예기치 못한 에러나 설계 충돌 발생 시, 임의로 계획을 왜곡하지 않고 상황을 보고한 뒤 필요한 조치를 취한다.
2. **사후 자체 검증 (Self-Verification Gate)**:
   - 코딩/작업 완료 후 테스트 실행, 빌드 검증, 문서 대조를 통해 사양서의 성공 기준을 100% 충족했는지 검증한다.
   - 오류 발생 시 자체 디버깅을 거쳐 완결 상태로 만든다.
3. **최종 워크스루 리포트 제공 (Walkthrough)**:
   - 작업 완료 후 다음 내용을 담아 사용자에게 최종 보고한다:
     - 완료된 작업 요약 및 변경된 파일 목록
     - 실행된 검증 결과 (테스트 성공 로그, 빌드 상태 등)
     - 사용자가 직접 확인해 볼 수 있는 방법 (실행 명령어, 확인 경로 등)
   - 출력 방식: 불필요한 파일 생성을 막기 위해 **채팅창 내 마감 보고서 출력**을 기본으로 한다. (사용자가 별도 파일 저장을 명시적으로 요청한 경우에만 `.agents/specs/walkthrough-{slug}.md` 생성)
